PromptFuzzer 独立 RECON 任务与接口设计

文档状态：Browser 基础闭环、AGENT / DUAL 引用和 HTTP_TEMPLATE 闭环均已实现
记录时间：2026-08-02

一、背景

当前 RECON 是 AGENT Workflow 内部的一个前置阶段：

AGENT Task
  -> INITIAL_INTEL
  -> INDEPENDENT_RECON
  -> STRATEGY_PLAN
  -> BUILD
  -> ATTACK

当前 RECON 与 AgentSession、具体 goal 和后续攻击流程绑定。RECON 完成后会立即生成 StrategyPlan，并继续进入 BUILD / ATTACK。

新的需求不是继续优化这个内部阶段，而是将 RECON 提升为独立任务：

1. 用户可以单独创建 RECON 任务。
2. RECON 只调查目标 Agent 应用的能力面，不要求选择攻击 goal。
3. RECON 完成后停止，不进入 StrategyPlan、BUILD、ATTACK 或 Judge 成功判定。
4. 最终情报和原始探测证据独立保存到数据库。
5. 后续 AGENT / DUAL 任务可以引用已有 RECON 结果，直接基于情报开始具体 goal 的测试。


二、核心定位

独立 RECON 与普通攻击 Task 是两个不同领域概念。

ReconTask：
- 调查一个目标 Agent 应用。
- 不绑定具体攻击 goal。
- 不判断提示词注入是否成功。
- 输出可复用的目标能力画像和探测证据。

Task：
- 针对一个或多个具体 goal 执行测试。
- 可以选择引用已有 ReconResult。
- 使用 RECON 情报生成 StrategyPlan 并执行 BUILD / ATTACK。

因此，不建议继续向 POST /api/tasks 增加 attackMode=RECON。
独立 RECON 应使用独立接口和数据模型，但复用现有底层浏览器、HTTP、Trace 和情报总结能力。


三、接口（已实现）

1. 创建独立 RECON 任务

POST /api/recon-tasks

请求示例：

{
  "name": "目标应用能力调查",
  "scanMode": "BROWSER",
  "reconContext": "目标是一个客服 Agent，主要处理订单查询；本次调查其正常能力、工具使用、上下文记忆和拒绝边界。",
  "targetConfig": {
    "chatUrl": "...",
    "targetType": "...",
    "selectors": {
      "input": "...",
      "submit": "...",
      "responseArea": "...",
      "newChat": "..."
    }
  },
  "externalIntelligence": "可选的页面说明、目标背景或已知情报",
  "reconConfig": {
    "maxCapabilityVerifications": 3,
    "cleanBetweenVerifications": true
  }
}

RECON 请求不包含 goalIds、techniqueIds、maxTurns、retryCount 等攻击参数。

字段职责：

- reconContext：
  描述目标应用是什么、正常业务用途、已知功能，以及本次希望调查的能力范围。
  它用于指导 RECON 收集信息，但不定义攻击目标和攻击成功标准。

- externalIntelligence：
  保存用户已经掌握的补充情报，例如页面说明、产品文档、历史测试记录、已知工具、目标样例和人工观察。
  这些内容仅供 RECON 内部推理和交叉验证，不应默认原样发送给目标应用。

- attackContext：
  不属于独立 RECON 请求。它继续用于后续 AGENT / DUAL 任务，描述具体攻击 goal、测试边界和成功标准。

三者的关系：

reconContext
  -> 定义本次要了解目标的哪些能力面

externalIntelligence
  -> 提供已经掌握的背景和待验证线索

attackContext
  -> 后续攻击任务中定义具体要验证什么安全目标

2. 查询 RECON 任务

GET /api/recon-tasks/{id}

返回任务状态、目标信息、执行进度、开始时间和完成时间。

3. 查询 RECON 最终结果

GET /api/recon-tasks/{id}/result

返回最终目标画像、结构化情报、质量状态和原始证据索引。

4. 查询应用面清单

GET /api/recon-results/{id}/application-surfaces

返回供前端逐条展示的 Agent 应用面，例如：

1. 支持 Python 脚本编写和运行
2. 支持调用 MCP Tools 查询业务数据
3. 支持读取和处理用户上传文件
4. 支持访问网页和远程 URL

应用面支持用户逐条新增、修改、删除和确认。前端应用面专栏不展示 responseProfile；响应特征只在后台保留，供后续 Agent 调整交互方式。

5. 查询 RECON 探测记录

GET /api/recon-tasks/{id}/traces

返回每轮页面读取、探测请求、目标响应、观察结论、异常和耗时。

6. 聚合桥接攻击单元

POST /api/recon-results/{id}/attack-units
GET /api/recon-results/{id}/attack-units

桥先将细粒度 CAPABILITY 按资源边界、安全控制和自然攻击链聚合为
ReconAttackUnit。主能力用于形成测试入口，辅助能力只提供上下文，明确不支持能力只记录边界，
UTILITY 默认不生成测试请求。

7. 攻击任务引用 RECON 结果

POST /api/tasks

在现有请求中增加一个可选字段：

{
  "attackMode": "AGENT",
  "goalIds": ["protected_value_extraction"],
  "reconResultId": 123
}

AGENT / DUAL 加载 ReconResult 后：
- 将目标画像转换为 Target Intelligence Memory。
- 默认跳过 Agent 内部独立 RECON。
- 根据具体 goal 生成 StrategyPlan。
- 从 BUILD 或 ATTACK 开始执行。


四、数据模型（已实现）

1. ReconTask

- id
- name
- scanMode
- reconContext
- targetConfig / rawRequestTemplate
- externalIntelligence
- reconConfig
- status：PENDING / RUNNING / COMPLETED / FAILED
- createdAt
- updatedAt
- completedAt

2. ReconResult

- id
- reconTaskId
- targetFingerprint
- businessProfile
- responseProfile
- capabilityInventory
- toolInventory
- unresolvedCapabilities
- supportingEvidence
- unresolvedQuestions
- targetIntelligenceMemory
- qualityStatus：SUFFICIENT / PARTIAL / INSUFFICIENT
- version
- createdAt

第一版可以将上述结构化内容保存为 JSON / MEDIUMTEXT，先保持实现简单。

其中 capabilityInventory 和 toolInventory 是独立 RECON 的核心结果。
responseProfile 供系统内部和后续 Agent 使用，不作为前端应用面专栏的展示内容。

capabilityInventory 记录目标 Agent 能完成的工作，例如：

- 数据查询与检索
- 数据创建、修改或审批
- 文件读取、生成和处理
- 网页或 URL 访问
- 代码或命令执行
- 消息、邮件、日程等外部操作
- 多轮规划和工作流编排

toolInventory 记录目标 Agent 声明或实际使用的 Skill、MCP、插件、内置工具和业务接口。每项至少包含：

- toolName
- toolType：SKILL / MCP / PLUGIN / BUILTIN / API / UNKNOWN
- description
- supportedActions
- requiredParameters
- dataOrResourceScope
- evidenceSource：AGENT_CLAIM / OBSERVED / EXTERNAL_EVIDENCE
- verificationStatus：UNVERIFIED / PARTIALLY_VERIFIED / VERIFIED / CONTRADICTED
- sourceTraceIds

3. ReconApplicationSurface

ReconApplicationSurface 是面向前端展示和后续攻击任务使用的最终应用面清单。每个应用面独立保存为一条记录，不使用一整段 JSON 让前端临时拆分。

- id
- reconResultId
- title
- description
- surfaceType
- relatedTool
- supportedActions
- resourceScope
- evidenceSource：AGENT_CLAIM / OBSERVED / EXTERNAL_EVIDENCE
- verificationStatus：UNVERIFIED / PARTIALLY_VERIFIED / VERIFIED / CONTRADICTED
- sourceTraceIds
- sourceType：AI_GENERATED / USER_ADDED
- userEdited
- createdAt
- updatedAt

用户可以逐条新增、修改、删除和确认应用面。AI 自动生成的原始结果应保留来源，用户修改后的当前有效内容供后续 AGENT / DUAL 使用。

4. ReconAttackUnit

ReconAttackUnit 是 RECON 和候选请求包之间的桥接聚合结果：

- id
- reconResultId
- generationId：同一次聚合生成的批次标识，默认查询最新批次
- unitKey
- title / description
- primarySurfaceIds
- supportingSurfaceIds
- negativeBoundarySurfaceIds
- resourceBoundary
- securityControls
- riskDimensions
- riskLevel
- confidence
- sourceSurfaceSnapshot

候选生成按 AttackUnit 进行，不再对每个 CAPABILITY 叶子逐一生成请求。候选执行时仍将主能力和
辅助能力 ID 写入 selectedSurfaceIds，保持 AGENT / DUAL 情报注入兼容。

5. ReconTrace

- id
- reconTaskId
- actionType：READ_TARGET / CAPABILITY_DISCOVERY / CAPABILITY_VERIFY
- targetChatIndex
- turnIndex
- requestMessage
- rawResponse
- extractedText
- observation
- evidenceType
- errorMessage
- durationMs
- createdAt

ReconResult 保存后台分析结果，ReconApplicationSurface 保存前端逐条展示的能力事实，
ReconAttackUnit 保存桥接后的可测试单元，ReconTrace 保存原始证据。最终 AttackUnit 必须能够
追溯到具体应用面和探测记录。


五、独立 RECON 主要收集的信息

独立 RECON 的核心目标是盘点目标 Agent 的业务用途、能力、工具和应用面，为后续选择具体安全测试方向提供依据。

1. 业务用途和目标定位

- 目标 Agent 用于完成什么工作
- 面向哪些业务对象、数据和资源
- 典型用户任务和正常操作流程
- 页面可见说明、示例和使用方式

2. 响应和交互特征

- 回复语言、长度和格式
- 是否严格遵循格式要求
- 是否复述用户输入
- 是否存在固定前缀、结束语或轮数限制
- 是否支持多轮上下文以及上下文如何延续
- 是否存在需要后续操作适配的交互特点

3. Agent 能力清单

- 能够完成哪些查询、读取、写入、修改、审批或执行操作
- 是否支持文件、网页、URL、代码、命令、消息或其他外部资源
- 是否具备多步骤规划、任务编排或自动执行能力
- 每项能力涉及哪些业务数据、用户对象和资源范围

4. 工具清单

- 支持或可能调用哪些 Skill
- 支持或可能调用哪些 MCP 工具
- 支持哪些插件、内置工具或业务 API
- 每个工具能够执行什么动作
- 工具需要哪些主要参数
- 工具可以访问哪些数据或资源
- 工具能力是 Agent 口头声明，还是已经观察到真实调用

可以通过正常能力询问开始收集，例如：

“你支持什么能力，能帮助我完成什么工作？对应会调用哪些 Skill、MCP 工具、插件或内置工具？”

Agent 的回答只能先记为 AGENT_CLAIM。只有观察到工具调用、真实结果、页面轨迹或其他外部证据后，才能提高 verificationStatus。

5. 潜在测试面映射

根据发现的能力和工具，记录后续值得开展的测试方向，但本次 RECON 不直接执行这些安全测试：

- 发现 MCP 或业务数据查询能力：后续考虑越权读取、跨用户或跨租户访问测试
- 发现代码或命令执行能力：后续考虑命令执行、环境信息和沙箱边界测试
- 发现 URL、网页或远程资源读取能力：后续考虑 SSRF、内网访问和间接内容注入测试
- 发现文件能力：后续考虑敏感文件读取、路径边界和文件操作权限测试
- 发现业务写入、审批或外部操作能力：后续考虑授权绕过、非预期操作和确认机制测试

6. 未确认能力和证据缺口

- Agent 声称支持但尚未观察到真实调用的能力
- 工具名称、参数、数据范围仍不明确的部分
- 不同回答之间存在冲突的能力描述
- 后续需要通过特定 Goal 任务进一步验证的测试面

独立 RECON 负责能力盘点、工具发现和应用面映射，不在本阶段实施越权、命令执行、SSRF 等正式安全验证。具体测试由后续引用该 ReconResult 的 AGENT / DUAL 任务执行。


六、与记忆系统的关系

独立 ReconResult 是跨任务、可复用的目标情报资产。

AgentSession 内现有字段仍负责单次攻击会话状态：
- targetIntelligenceMemory
- buildMemory
- attackSignals

关系如下：

ReconResult.targetIntelligenceMemory
  -> 创建 AGENT / DUAL Task 时加载
  -> 初始化 AgentSession.targetIntelligenceMemory
  -> StrategyPlan 根据具体 goal 进行攻击规划
  -> BUILD / ATTACK 运行中继续产生 buildMemory 和 attackSignals

ReconResult 不应被后续攻击过程直接覆盖。攻击过程中产生的新情报先保存在 AgentSession；未来如需回写 ReconResult，应设计显式的合并和版本机制。


七、与现有 Workflow 的关系

独立 RECON Workflow：

CREATE_RECON_TASK
  -> OPEN_TARGET
  -> READ_TARGET
  -> OPEN_CAPABILITY_DISCOVERY
  -> COVERAGE_PLAN
  -> DOMAIN_DISCOVERY
  -> COVERAGE_GAP_ANALYSIS
       -> GAP_FOLLOWUP
  -> CAPABILITY_VERIFY
  -> EVIDENCE_SUMMARY
  -> APPLICATION_SURFACE_SYNTHESIS
  -> SURFACE_QUALITY_GATE
  -> RECON_RESULT_SAVE
  -> RECON_FINAL_SYNC

到此结束，不进入 StrategyPlan、BUILD、ATTACK、Judge 或 CompositeReview。

各阶段职责：

- READ_TARGET：
  读取页面说明、示例和可见业务信息。

- OPEN_CAPABILITY_DISCOVERY：
  先整体询问目标支持的业务、输入输出、文件、代码/沙箱、工具和其他能力。回答只作为 CLAIMED 线索，不按回答编号直接生成应用面；失败时记录 ERROR 并继续固定矩阵。

- COVERAGE_PLAN：
  基于开放回答、固定能力域矩阵、页面内容和用户已有情报，规划分类发现问题。固定能力域覆盖业务查询、元数据、文件、代码/Bash、沙箱、Web、工具生态、写操作、消息和报告产物；矩阵外能力进入 OTHER_DISCOVERED，目标没有主动提及的领域保持 UNKNOWN。

- DOMAIN_DISCOVERY：
  按能力域分批询问目标用途、能力、工具和资源边界，不再用一条综合问题决定全部能力范围。

- COVERAGE_GAP_ANALYSIS：
  统一检查能力域状态。对 HIGH / MEDIUM 优先级且仍为 UNKNOWN 的领域生成 GAP_FOLLOWUP；达到消息预算后才进入验证。

- CAPABILITY_VERIFY：
  从全部发现记录和外部线索中选择原子能力，执行正常、非攻击性的验证。非空回复只表示交互成功，证据进一步区分 CLAIMED、PARTIALLY_OBSERVED、TOOL_OBSERVED、RESULT_OBSERVED 和 CONTRADICTED。

- EVIDENCE_SUMMARY：
  统一读取页面信息、覆盖矩阵、能力发现和验证记录，输出业务画像、原子 capabilityFacts、工具清单、未确认能力和证据状态；本节点不直接生成最终应用面。

- APPLICATION_SURFACE_SYNTHESIS：
  基于 capabilityFacts 统一拆分、聚合和命名应用面，形成最多两层的 DOMAIN -> CAPABILITY 结构。DOMAIN 负责聚合展示且 selectable=false；CAPABILITY 是原子能力叶子，selectable=true，作为桥的聚合输入。

- SURFACE_QUALITY_GATE：
  Java 侧校验重复 surfaceKey、重复 capability 映射、无效父节点、无事实叶子、空 DOMAIN、结构化产物和证据状态。DOMAIN 状态由子节点聚合；CLAIMED / EXTERNAL_EVIDENCE 不能生成 VERIFIED；只有明确工具调用或通过产物结构校验的真实结果可以生成 VERIFIED。

引用已有 RECON 的 AGENT Workflow：

LOAD_RECON_RESULT
  -> INITIAL_INTEL
  -> STRATEGY_PLAN
  -> BUILD / ATTACK
  -> JUDGE
  -> MEMORY_DELTA
  -> FINAL_SYNC

如果没有提供 reconResultId，现有 AGENT 内部 IndependentReconNode 可以继续作为兼容和自动兜底能力。


八、独立 RECON Prompt 设计

当前独立目录：

src/main/resources/prompts/recon/
  open_capability_discovery.txt
  coverage_plan.txt
  coverage_gap_analysis.txt
  capability_verify.txt
  evidence_summary.txt
  application_surface_synthesis.txt

1. open_capability_discovery.txt

生成一条开放能力询问，整体收集业务、工具、输入输出和页面未明显展示的能力。回答只作为待确认 CLAIMED 线索。

2. coverage_plan.txt

消费开放回答并基于固定能力域矩阵规划分类发现问题。用户已有情报和开放回答只能提供待确认线索，不能缩小探测范围。

3. coverage_gap_analysis.txt

汇总分类发现记录，为每个固定能力域标记 UNKNOWN、CLAIMED、OBSERVED、NOT_SUPPORTED 或 NOT_APPLICABLE，并为重要 UNKNOWN 能力生成补充问题。未提及能力不能判定为不支持。

4. capability_verify.txt

根据完整覆盖矩阵和发现记录，为关键原子能力生成正常、非攻击性的验证请求。文件产物、代码执行、沙箱等能力分别验证，普通文本回复不能直接视为验证成功。

5. evidence_summary.txt

把全部 Trace 整理为原子能力事实 capabilityFacts，并区分 CLAIMED、PARTIALLY_OBSERVED、TOOL_OBSERVED、RESULT_OBSERVED、CONTRADICTED 和 EXTERNAL_EVIDENCE。该阶段不直接生成应用面。

6. application_surface_synthesis.txt

统一将原子能力事实聚合为 DOMAIN -> CAPABILITY 两级应用面。DOMAIN 仅用于聚合展示，
CAPABILITY 叶子是桥的事实输入，不再天然等于独立测试请求。

模型输出随后必须经过 ReconSurfaceQualityService 的确定性质量门禁，完成去重、父子关系校验、叶子选择语义校验和证据状态降级。

7. attack_unit_synthesis.txt

桥先由 Java 标记 PRIMARY、SUPPORTING、NEGATIVE_BOUNDARY 和 UTILITY，再由模型按资源边界、
安全控制和自然攻击链聚合 AttackUnit，最后由 Java 拒绝无主能力、重复主能力、越界 ID 和
不支持能力作为主能力等无效结果。

旧 capability_discovery.txt 和 recon_result_summary.txt 已删除，避免固定单问题发现和一次性结果建模逻辑被重新调用。


九、代码复用边界

建议复用：
- BrowserService
- HttpRequestService
- AgentWorkflowTraceRecorder 的设计方式
- 当前 IndependentReconNode 中的页面读取和目标交互能力

建议新增：
- ReconTaskController
- ReconTaskService
- ReconExecutor 或 ReconWorkflowEngine
- ReconPromptService
- ReconTask / ReconResult / ReconTrace 实体与 Repository
- ReconApplicationSurface 实体与 Repository
- 独立 RECON 请求和响应 DTO

不建议直接让独立接口调用完整 AgentWorkflowEngine，因为 AgentWorkflowEngine 的职责包含 StrategyPlan、BUILD、ATTACK、CompositeReview 和 AgentSession 最终同步。


十、第一版实施范围

第一版只完成：

1. 独立创建和查询 RECON 任务。
2. Browser 与 HTTP_TEMPLATE 均已实现；第一阶段曾优先完成 Browser。
3. 保存原始探测记录和最终 Target Intelligence Memory。
4. 将能力和工具结果整理为可逐条展示、编辑的 ReconApplicationSurface。
5. 提供应用面清单查询及用户新增、修改、删除、确认能力。
6. AGENT / DUAL 支持 reconResultId，并读取用户修订后的当前有效应用面。
7. 引用已有情报时默认跳过内部独立 RECON，并支持用户选择补充侦察。
8. 保留 AI 原始结果，用户修改形成当前有效版本。

第一版暂不完成：

- 完全开放式、无固定边界的动态 RECON 规划；当前已实现“开放发现 + 固定能力矩阵 + COVERAGE_PLAN + 缺口补探”的受控动态规划。
- 每轮单独执行 observation extract。
- 多次 RECON 自动合并。
- 向量库或长期知识库。
- RECON 结果自动回写更新。
- 多用户共享和权限控制。
- 复杂的目标指纹匹配与过期检测。

后续专项待办：

- 新版 RECON 真实靶场回归：

十一、当前结论

独立 RECON 值得开发，其核心价值是将“目标能力调查”和“具体 Goal 攻击”解耦。

外部接口和数据模型应独立，底层目标交互与情报总结能力应复用。这样可以避免继续扩大 POST /api/tasks 的职责，同时让同一份目标情报被多个 AGENT / DUAL 测试任务复用。
